# Shared agent rules — iina

Initialized on 2026-10-13 from repository evidence using project-init.

## Working agreement

- Read [README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md) before changing the project. Preserve their contribution and licensing requirements.
- Match the existing English project documentation and source style; respond in the user's language.
- Keep changes focused and evidence-based. Never invent commands, versions, test coverage or architectural relationships.
- Do not stage or commit credentials, local runtime data, private task context or user preferences without explicit authorization and review.
- Changes to this file, AGENTS.md, CLAUDE.md and README.md require user authorization; an explicit documentation or initialization request supplies that authorization within its scope.

## Skill routing

When available, use `sdd-riper-one-light` for medium or larger development tasks: a minimal spec, an execution checkpoint, relevant validation and result writeback. Mechanical single-file edits need no elaborate process.
Use `codemap` for unfamiliar module navigation, project maps and terrain changes. Keep maps under `mydocs/codemap/` and task records under `mydocs/specs/`; maps are indexes, source remains authoritative.
Use `mermaid` for diagrams when available; otherwise follow [Mermaid rules](docs/knowledge/mermaid-rules.md) and self-check syntax. Follow [Karpathy guidelines](docs/knowledge/karpathy-guidelines-en.md) for focused implementation.

## Code exploration

When `.codegraph/` exists, use `codegraph explore "<symbol, path or question>"` (or the equivalent MCP tool) before text search or file reads to understand or locate code. Use `codegraph status` to check freshness and `codegraph index` to synchronize changed files. Never delete the index to rebuild it without explicit permission.
Use text search for configuration, strings, unsupported files or gaps in the graph; verify relationships against current source. If no index exists, do not initialize it without a user request.

## Repository constraints

- Only VideoView and MPVController may call mpv APIs directly. PlayerCore owns playback logic; use its operations instead of setting mpv options from unrelated layers.
- MainWindowController owns window lifecycle logic. Prefer UIHelper and ConstraintsSugar over adding or modifying XIB files.
- Do not hand-edit MPVCommand.swift, MPVOption.swift or MPVProperty.swift; they are generated by other/parse_doc.rb when updating libmpv.
- Follow the existing two-space indentation. Localized source changes belong in Base.lproj and en.lproj; other translations are managed through Crowdin.
- Preserve CONTRIBUTING.md requirements for design proposals, focused pull requests, testing and AI disclosure. Do not send external messages or publish a PR unless authorized.
- Use existing build/check tools. Report unavailable checks explicitly; an index or successful documentation check does not prove playback behavior.
